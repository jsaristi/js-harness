## Findings: high

### H1. `uninstall machine` removes idle background sessions with no worktree guard

- **What:** `uninstall machine` calls `undoBackground` (`bin/install.mjs:673`), which runs `undoSession` on every
  recorded background session that is not at work (`bin/lib/background.mjs:429-439`); `undoSession` runs `claude
  stop` and then `claude rm` (`bin/lib/background.mjs:381-405`). Nothing on that path asks whether the session's
  worktree holds work. `sessions stop` does: it refuses while the worktree holds changes, and its own message says
  why, "claude rm deletes them even when it says it refused (2026-11-04)" (`bin/sessions-background.mjs:429-436`).
- **Evidence:** the four places above, read. `odd/tasks/stop-keeps-worktree.md:89` (L2) names the uninstall path as
  a follow-up to open; that document's tasks T1 to T3 are all ticked, so no open box holds it.
- **Why it matters:** uncommitted work in a background session's worktree is deleted by a command whose purpose is
  to undo the harness, not to discard work. The trigger is rare (an uninstall while a background session sits idle
  with changes), and the loss is not recoverable.
- **Proposed action:** give `undoSession`, or its caller in `undoBackground`, the same `worktreeHolding` refusal,
  with the test that proves it; keep and name the session as `uninstall machine` does for other things it cannot
  undo exactly.
- **Whose call:** the lead's to schedule; it is a defect, and the fix is the guard that already exists.
- **Mark:** checked (read; not reproduced, since reproducing it deletes a worktree).

### H2. The backup's secret blanking misses common key shapes, and the bundles are pushed as they are

- **What:** `redactSecrets` (`bin/lib/backup.mjs:28` onward) blanks an API key only when its pattern matches, and
  the pattern does not match a key whose random part holds `_` before a hyphen. The other patterns
  (`bin/lib/backup.mjs:37`) cover a short list of field names.
- **Evidence:** the function run on synthetic values. Unchanged: `sk-ant-api03-Ab1c_<12 chars>-<36>-<36>`;
  `sk-proj-Ab_cD-<…>`; `Authorization: Basic <base64>`; a password inside `https://user:pass@host/`; `DB_PASS=<…>`;
  `glpat-<…>`; `AIza<…>`; `sk_live_<…>`; `npm_<…>`. Blanked: a plain `sk-<36>`, `sk-ant-api03-<36>` with no
  underscore, and any value behind a credential-named field. Separately, `bin/backup.mjs:39-43` (the help) says
  the backup goes out with "secrets blanked", while `bin/lib/backup-repos.mjs:179` runs `git bundle create` and
  the bundle is pushed as it is.
- **Why it matters:** transcripts hold whatever a session printed or was shown. A key of those shapes in a
  transcript reaches the backup repository in clear. The exposure is bounded: the backup repositories are
  private, so this is a secret at rest in a private remote, not a public leak. The help's sentence is not true
  for the bundles.
- **Proposed action:** widen the key pattern to the real alphabets of the named providers (`[A-Za-z0-9_-]`), add
  the missing shapes, and add the test the reader found missing (`bin/lib/backup.test.mjs:28` feeds no key with
  `-` or `_` in its random part); say in the help that bundles are not blanked, or scan them.
- **Whose call:** his (security, and what leaves his machine).
- **Mark:** checked (ran the pure function; the reader ranked the pattern gap high and this session agrees,
  with the bound said).
