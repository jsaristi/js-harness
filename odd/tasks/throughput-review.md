The throughput review protocol: a command that measures where the time goes, the recorders it needs, a daily trigger, and the protocol's section in the skill.
Branch: feat/throughput-review (from origin/main ead4e8d). Delivery: ask-on-risk, one PR per unit. Tests: `node --test`.

## Goal
The question "where does the time go and what is worth changing" is answered the same way every day by
`js-harness throughput`, from dated snapshots that outlive the rotating logs, triggered by the lead's heartbeat and
not by its memory, so that a proposal reaches him only with measured numbers that two readers checked.

## Why
The 2026-10-15/16 measure (`throughput-v3-measure.md` in the lead's notes) took one analyst and two readers an evening
of hand-written scripts, and its baseline survives only because the lead copied the logs by hand: the gate log keeps
about 2.3 days (`gate-log-size`, 512 KiB). Several facts it needed were logged nowhere (CI fallbacks, per-file test
times, when a question was shown and answered, how long a gentle-ai review took). He asked for "un protocolo estricto
y preciso" and approved it on 2026-10-17 ("Sí, aprobalo (Recomendada)").

## Constraints
- Read-only except the snapshot folder and the recorders' lines — because a measure that writes where the work lives can change what it measures.
- Every figure names its source, and a fact no record holds prints `not recorded (<recorder>, <owner>)`, never a zero — because a missing figure read as zero is how the "0 Windows runs per land" premise survived.
- No check, review or test is removed or weakened (his hard limit for every item).
- What is written outside the repository lives in one folder under the harness home, removed by `uninstall` — because the predecessor needed four purge scripts (AGENTS.md).

## Design (version 1, for two readers)

### Unit 1 · `js-harness throughput`
- `js-harness throughput [--since <YYYY-MM-DD>] [--until <YYYY-MM-DD>] [--json]`: the window is whole UTC days,
  `[since 00Z, until 00Z)`, by default the previous UTC day. Read-only. For each day it takes the day's snapshot when
  there is one, otherwise it reads the live records, and its header says which, per day. A live day whose gate log
  begins after 00Z (rotation) is marked `partial: the gate log begins at <time>` on every gate row.
- `js-harness throughput snapshot [--day <YYYY-MM-DD>]`: writes the facts of one closed UTC day (default yesterday)
  to `<home>/.js-harness/throughput/<project slug>/<day>.json`, once: an existing snapshot is never rewritten (exit 1,
  it says so), so a before/after never drifts; an unclosed day is refused (exit 2). The only verb that writes.
- `js-harness throughput status`: the snapshots there, each partial one with why, and the days between the first
  snapshot and yesterday that have none (exit 1 when one is missing): the missing-day check.
- A snapshot holds facts, not figures: the day's gates (from the gate log: kind, lock, start, end, seconds, waited,
  session, result, where the tests ran, failing names), its merged PRs (number, merged at, last commit at), its Codex
  runs, its questions, its notices by kind, the open and done task counts at 00Z and 24Z, the merges of main into
  branches that conflicted with their files, and what each recorder of unit 2 adds. The table is a pure function of the
  facts of the window's days, so a window of snapshots and a window of live days print the same way, and medians over
  several days are medians of the facts, not of the daily medians.
- Sources, each named on its row: the gate log (`readGateLog`, `gatesOf`); `git log origin/main` as last fetched
  (the command fetches nothing, and prints the ref's commit and its age); `<git common dir>/js-harness/codex-review-runs.jsonl`;
  the channel record (`readNotices`); `git ls-tree` of `odd/tasks/*.md` and `docs/ROADMAP.md` at the first-parent
  commit before each bound (the measure's method); `git merge-tree --write-tree` of each non-PR merge on main's history.
- Gate kinds, as the measure classified them: a land (`merge-queue` in its folder), a session check (`check`), a
  wrapped commit (`gate -- git commit`), the lead's copy update (`update-copy`), any other `gate --` run.
- The fixed rows, in order: PRs merged (and per hour); last commit to merged (median, worst); ready to merged (B1,
  JH 26: `not recorded` until its notices carry a PR number); lock busy hours (union of own-lock runs); waits (total,
  the three sessions that waited most); commit gates local vs GitHub (medians, CI fallbacks from B3); lands (count,
  median suite, red with failing names; phases `not recorded (B2, JH 24)`); top failing test names; slowest test files
  (B5); Codex (runs, median and p90 seconds, minutes); gentle-ai (lineages, median minutes, B6); questions (recorded to
  shown, shown to answered, B4); idle sessions with nothing armed (`not recorded (B8)`); tool calls open > N min
  (`not recorded (G, JH 26)`); tasks closed and added; conflicts by file.
- `--against <YYYY-MM-DD>..<YYYY-MM-DD>` (S6): prints the before window beside, and marks a change that stays inside
  the range of the before window's daily values `within noise`. The noise band is measured from the before window
  itself (it needs at least two days), so it carries no constant to declare; items shipped in one window are compared
  together, since the windows are what is compared.

### Unit 2 · the recorders
- B3, in `testsOnCi`: when CI gives no answer, one gate-log line of a new kind `ci-fallback` `{ why }` (a reader of
  an older version skips a kind it does not know: `readGateLog`); on the CI end line the tests sensor carries `failing`
  from CI's output (`failingTests`), a field the end line already has. Coordinated with the commit-gates session, which
  owns C in the same file.
- B4, in `notify --kind answer --question <n>`: the answer notice keeps `shownAt` (the question-tool call's time,
  `answered.askedAt`) and `answeredAt` (the time of the user's line), which `copyOfAnswer` already reads from the
  transcript and drops today; a typed answer has no `shownAt`. The question notice's `at` stays "recorded at".
- B5, the per-file test times: the tracer's per-file results file (`trace-reads.cjs`) gains the file's seconds
  (`process.uptime()` at its exit), and the gate writes `{ id, files: [{ test, seconds }] }` to a file of its own beside
  the log, `test-times.jsonl`, rotated by the same bound into `test-times.1.jsonl`, as `busiest.jsonl` is: a whole
  list of about 150 files on every end line would shrink the log's 2.3 days. Only gates that trace (exact tests on)
  record it.
- B6, gentle-ai (revised in L25 and L26): the harness never runs a review, and gentle-ai deletes a transaction when it
  burns it, so the start is lost. gentle-ai keeps each live transaction as a folder `<git common dir>/gentle-ai/review-transactions/v2/<lineage>/`,
  made at START, and writes one `terminal-consumption/v1/<hash>.json` naming the lineage before it deletes that folder
  at the burn. The PostToolUse hook already installed (`resume --pause`, every tool, sub-agents' calls too, in a project
  with `harness.json` whose common dir is found by files) lists `v2/`, keeps the folders whose names are lineage ids
  (`^[a-z0-9]+(?:-[a-z0-9]+)*$`, not `LOCK` nor temporary entries), and appends `{ v, lineage, at, from }` for each
  lineage and birthtime it has not recorded to `<home>/.js-harness/throughput/<slug>/review-starts.jsonl`, the folder
  made only when there is a line to write. `at` is the folder's birthtime (`from: "birthtime"`) when it is above 0, not
  after the folder's mtime nor now, and, outside Windows and macOS, not its ctime; the hook's own time otherwise
  (`from: "seen"`). `throughput` finds the common dir with git, and reads: a lineage acknowledged when its terminal
  record is there and its folder is gone (ended at the record's birthtime); open when its folder is there; gone
  without acknowledgement when its folder went with no record (abandoned, reclaimed or reset). Per day: started (the
  starts recorded, a lower bound, since a review started and burned inside one tool call is never seen by the hook;
  `not recorded` before B6 reached main), acknowledged (from the records, so days before B6 count), median minutes
  from start to acknowledgement per lineage (a recovered review continues under a new lineage, so a duration is one
  lineage's), open and gone. Reviews any session started are covered, whoever ran them, when a Claude session of the
  project made a tool call while the folder was there. A record restored from a copy carries the copy's birthtime.

### Unit 3 · the daily trigger
- The heartbeat, at its start and on each tick, writes the snapshot of each closed day since the first snapshot that
  has none (at most the last 14 days; a day the gate log no longer covers is written partial and says from when).
  So the record does not depend on the lead; a missing day is one the heartbeat did not run through, and status names it.
- It ends with `DUE: throughput review of <day>: js-harness throughput --since <day>; js-harness-protocols section 7`
  (exit 0) when the review of the last closed day is due and not recorded. The lead records each review with
  `js-harness throughput reviewed --day <day> --found nothing|candidates`, appended to `reviews.jsonl`'s neighbour
  `outcomes.jsonl`. Due is daily, and weekly (seven days after the last recorded review) once the last two recorded
  reviews found nothing (S4's stop rule, the rule `throughput-quiet-runs`, 2); one that found candidates makes it daily again.
- A heartbeat started while the review is due ends at once with the DUE line: the trigger is one command away from
  cleared (`reviewed`), and a line printed into a background task's file that the lead reads only at its end would not
  be seen.
